# البنية المعمارية — REC Smart Audio

## 1. نظرة عامة

```
                        الإنترنت / الشبكة الداخلية
 ┌──────────────┐  HTTPS + WSS   ┌───────────────────────────────────────────┐
 │ متصفح/جوال    │ ─────────────▶ │  Caddy (TLS تلقائي)  :443                  │
 │ المستخدم      │ ◀───────────── │        │                                   │
 └──────────────┘   /ws (مباشر)   │        ▼                                   │
                                  │  REC Server (Node.js 20+, Fastify)  :4000  │
                                  │   ├─ REST API  /api/*                      │
                                  │   ├─ WebSocket المتصفح   /ws                │
                                  │   ├─ WebSocket الأجهزة    /ws/agent         │
                                  │   ├─ لوحة التحكم (Next.js static export) / │
                                  │   └─ تخزين الملفات الصوتية  /data/audio    │
                                  │        │                                   │
                                  │        ▼                                   │
                                  │  PostgreSQL 16 (Prisma ORM)                │
                                  └───────────────────────────────────────────┘
                                             ▲  اتصال صادر فقط (WSS + HTTPS)
                                             │  رمز مصادقة خاص بكل جهاز
 ┌───────────────────────────────────────────┴─────────────┐
 │  داتا سنتر المؤسسة — جهاز التشغيل (Windows / Linux)        │
 │  REC Audio Agent (Python)  — خدمة نظام تعمل دائمًا         │
 │   ├─ Scheduler محلي (الأذان + الجداول) يعمل دون إنترنت      │
 │   ├─ Priority Queue (أذان > طوارئ > إعلان > عام)           │
 │   ├─ Player (pygame/SDL2) ← مخرج صوت: Bluetooth/AUX/USB    │
 │   ├─ Offline Cache (ملفات + إعدادات + سجلات SQLite)        │
 │   ├─ Bluetooth Reconnect + Watchdog + Health               │
 │   └─ مزامنة السجلات عند عودة الاتصال (بلا تكرار)           │
 └──────────────────────────┬──────────────────────────────┘
                            ▼
                سماعات الممرات (مكبر صوت/مازج)
```

### لماذا هذا التقسيم؟

| القرار | السبب |
|---|---|
| لوحة Next.js تُبنى كملفات ثابتة (`output: "export"`) ويقدّمها خادم Node نفسه | مصدر (origin) واحد للواجهة والـ API والـ WebSocket ⇐ لا CORS، كوكيز آمنة `SameSite=Strict`، ونشر أبسط بحاوية واحدة. |
| Backend مستقل (Fastify) وليس API Routes داخل Next.js | يحتاج النظام اتصال WebSocket دائمًا مع الأجهزة ومؤقتات في الخلفية، وهذا لا يناسب بيئات serverless. |
| الجهاز المحلي هو من يتصل بالخادم (Outbound) | لا حاجة لفتح أي منفذ وارد في شبكة الداتا سنتر؛ يكفي السماح بـ HTTPS صادر إلى نطاق الخادم. |
| الجدولة والأذان يُنفَّذان **محليًا** على الجهاز | الخادم يرسل "خطة" محسوبة لـ 60 يومًا؛ الجهاز ينفّذها حتى لو انقطع الإنترنت أو توقف الخادم. وعند تجاوز الخطة يحسب أوقات أم القرى بنفسه. |
| مفتاح حدث حتمي `eventKey` لكل تشغيل | يمنع تكرار الأذان/الإعلان، ويجعل مزامنة السجلات بعد الانقطاع idempotent (فهرس فريد `deviceId + eventKey`). |

## 2. المكوّنات

### 2.1 الخادم `server/`
- **Fastify 5 + TypeScript**، تحقق المدخلات بـ **zod**.
- **Prisma 7** مع `@prisma/adapter-pg` (عميل بلا محرك Rust).
- **المصادقة**: كلمات مرور bcrypt (12 جولة) + جلسات في قاعدة البيانات (رمز عشوائي 256-bit، يُخزَّن مُجزّأً SHA-256) في كوكي `HttpOnly; Secure; SameSite=Strict`. قفل الحساب بعد 5 محاولات فاشلة لمدة 15 دقيقة، وتحديد معدل الطلبات على تسجيل الدخول.
- **الصلاحيات (RBAC)**: `SUPER_ADMIN` / `AUDIO_MANAGER` / `VIEWER` تُفحص في كل مسار.
- **أوقات الصلاة**: مكتبة `adhan` بطريقة أم القرى (فجر 18.5°، عشاء = مغرب + 90 دقيقة، و+120 في رمضان حسب تقويم أم القرى الهجري)، ثم تطبيق: الوقت الثابت اليدوي ← تعديل التاريخ المحدد ← الإزاحة بالدقائق.
- **Hub**: يدير اتصالات WebSocket للمتصفحات والأجهزة، يوزّع الأوامر ويبث الحالة لحظيًا.
- **الأوامر**: تُحفظ في جدول `Command` بحالة (PENDING→SENT→ACKED/FAILED/EXPIRED) ومهلة صلاحية، فلا يُنفَّذ أمر "تشغيل" قديم بعد عودة جهاز منقطع.

### 2.2 جهاز التشغيل `agent/`
- Python 3.10+، `asyncio`، `websockets`، `httpx`، `pygame` (SDL2 لاختيار مخرج الصوت).
- يعمل كخدمة: **systemd (user service + linger)** على Linux، و**Windows Service عبر NSSM** على Windows.
- **SQLite محلي** لحفظ: آخر إعدادات، الأحداث المنفّذة، السجلات غير المُزامنة، الأوامر المستلمة.
- **Watchdog** داخلي (خيط مستقل يراقب نبض الحلقة الرئيسية ويعيد تشغيل العملية عند التعليق) + `WatchdogSec` في systemd + إعادة تشغيل تلقائية في NSSM.

### 2.3 لوحة التحكم `web/`
- Next.js 16 (App Router) + TypeScript + Tailwind CSS 4، عربية RTL افتراضيًا مع ملف ترجمة إنجليزي، وضع ليلي/نهاري، متجاوبة.
- تحديث مباشر عبر `/ws`.

## 3. قاعدة البيانات

الملف المرجعي: [`server/prisma/schema.prisma`](../server/prisma/schema.prisma)

| الجدول | الغرض |
|---|---|
| `User` | المستخدمون، الدور، القفل بعد المحاولات الفاشلة |
| `Session` | الجلسات النشطة (قابلة للإلغاء فورًا) |
| `AudioFile` | المكتبة الصوتية: التصنيف، المدة، الحجم، SHA-256 للتحقق عند التنزيل |
| `PrayerSettings` | الموقع وطريقة الحساب (سجل واحد) |
| `PrayerConfig` | لكل صلاة: تفعيل، ملف الأذان، مستوى الصوت، إزاحة، وقت ثابت |
| `PrayerOverride` | تعديل وقت صلاة في تاريخ محدد (مطابقة تقويم أم القرى) |
| `SystemSettings` | سياسات التشغيل: ما بعد الأذان، الطوارئ، حدود الصوت، مهلات التعويض، `configRevision` |
| `Device` | أجهزة التشغيل، رمز المصادقة (مُجزّأ)، المخرج، الحالة الأخيرة |
| `Schedule` (+`_ScheduleDevices`) | الجداول: مرة/يومي/أسبوعي، وقت ثابت أو نسبة لصلاة، فترة سريان، إيقاف مؤقت، أجهزة مستهدفة |
| `Command` | الأوامر المرسلة للأجهزة وحالتها |
| `PlaybackLog` | سجل التشغيل — فريد على `(deviceId, eventKey)` |
| `AuditLog` | سجل عمليات المستخدمين |

```
User 1─* Session        User 1─* AudioFile      AudioFile 1─* Schedule
User 1─* Command        Device 1─* Command      Device 1─* PlaybackLog
Schedule *─* Device     AudioFile 1─* PrayerConfig
```

## 4. بروتوكول الاتصال بين الخادم والجهاز

الاتصال: `wss://<server>/ws/agent` مع ترويسة `Authorization: Bearer <device-token>`.
كل رسالة JSON بالشكل `{ "type": "...", ... }`. التفاصيل الكاملة في [PROTOCOL.md](PROTOCOL.md).

```
Agent                                   Server
  │── hello {os, version, outputs} ───────▶│  يتحقق من الرمز، يسجّل الجهاز Online
  │◀────────────── welcome {serverTime} ───│  (لقياس فرق الساعة)
  │◀──────── config {revision, plan, ...} ─│  الخطة: أذان 60 يومًا + الجداول + الملفات
  │── GET /api/agent/files/:id ───────────▶│  تنزيل الملفات الناقصة + تحقق SHA-256
  │── config_applied {revision} ──────────▶│
  │◀──────────── command {id, type, ...} ──│  تشغيل/إيقاف/صوت/اختبار...
  │── ack {commandId, ok} ────────────────▶│  → يُبث للمتصفحات
  │── status {...} (كل 10ث وعند كل تغيير) ─▶│  → يُبث للمتصفحات
  │── events [{eventKey, status...}] ─────▶│  upsert بلا تكرار
  │◀────────────── events_ack {keys} ──────│  الجهاز يعلّمها "مُزامنة"
```

عند الانقطاع: يستمر الجهاز بالخطة المخزنة، ويعيد المحاولة بتأخير أُسّي (1ث → 60ث). عند العودة: يرسل `hello` ثم كل الأحداث غير المزامنة، ويستلم أحدث `config`.

## 5. أولوية التشغيل (Audio Priority Queue)

| الأولوية | النوع | السلوك |
|---|---|---|
| 1 | الأذان | يقطع أي صوت فورًا. لا يُقطع إلا بأمر صريح من Super Admin. |
| 2 | الطوارئ المصرّح بها | تقطع الإعلانات والعامة. أثناء الأذان: تُضاف أول الطابور لتعمل فور انتهائه — إلا إذا فُعّل "السماح للطوارئ بمقاطعة الأذان" **و** أرسلها Super Admin بخيار المقاطعة. |
| 3 | الإعلانات الإدارية | تقطع الصوتيات العامة (التي تُستأنف بعدها). |
| 4 | الصوتيات العامة | تعمل عند عدم وجود ما هو أعلى. |

- **لا تداخل**: مشغّل واحد لكل جهاز؛ العناصر ذات الأولوية المساوية أو الأقل تنتظر في طابور مرتب (أولوية ثم وقت الإضافة) ولها مدة صلاحية (`queuedItemTtlMinutes`).
- **بعد الأذان** (`postAdhanBehavior`): `RESUME` استئناف من نفس الموضع، `RESTART` إعادة من البداية، `DISCARD` تجاهل. ويمكن تحديد فترة هدوء بعد الأذان (`postAdhanQuietMinutes`) تُؤجَّل خلالها الصوتيات العامة والإعلانات.
- **منع التكرار**: `adhan:YYYY-MM-DD:PRAYER` و`sched:<id>:YYYY-MM-DDTHH:mm` تُحفظ محليًا قبل بدء التشغيل؛ إعادة تشغيل الجهاز أو تكرار الرسالة لا يعيد الحدث.
- **التعويض بعد الانقطاع**: إذا أُعيد تشغيل الجهاز بعد دخول الوقت بقليل، يُشغَّل الأذان إن كان التأخير ضمن `adhanCatchUpMinutes` (افتراضي 3 دقائق) ولم يُنفّذ سابقًا؛ وإلا يُسجّل `SKIPPED`.

## 6. الأمان (ملخص — التفاصيل في [SECURITY.md](SECURITY.md))
- HTTPS إلزامي عبر Caddy (شهادة Let's Encrypt تلقائية) و HSTS.
- لا منافذ واردة في الداتا سنتر: الجهاز يتصل صادرًا فقط.
- رمز لكل جهاز (32 بايت عشوائية) يظهر مرة واحدة ويُخزّن مُجزّأً؛ إلغاؤه يقطع الاتصال فورًا.
- تسجيل كل العمليات في `AuditLog`، وتحديد معدل الطلبات، وترويسات أمان (Helmet/CSP)، والتحقق من نوع الملف الصوتي من محتواه (magic bytes) لا من امتداده.
